## СЛАЙД 2 — Постановка задачи

**Заголовок:** Две принципиально разные задачи — два разных инструмента

- Данные строго типизированы

- Граф пререквизитов между дисциплинами

- SQL-рекурсия на глубоких деревьях — дорого и медленно

**Решение (в центре, акцентным цветом):** Polyglot Persistence: PostgreSQL + Neo4j

---
**[ТЕКСТ]**
> «Перед нами стояло две задачи. Первая — надёжно хранить строго структурированные данные: учебные планы, студентов, их оценки, семестры. Здесь нам нужны транзакции и гарантии консистентности. Вторая задача — анализировать граф зависимостей между дисциплинами: если "Матан 2" требует "Матан 1", а тот — "Школьную алгебру", то поиск всей цепочки через рекурсивные JOIN — это очень тяжело. Поэтому мы применили паттерн Polyglot Persistence: каждая СУБД делает то, в чём она сильна.»

## СЛАЙД 3 — Архитектурная схема

**Заголовок:** Архитектура системы  
**Схема (три блока со стрелками):**

```
[PostgreSQL]          [ETL: migrate.py]        [Neo4j]
  Учебные планы    →   Полная ресинхрони-    →   Граф зависимостей
  Студенты             зация при каждом          Рекомендационный
  Оценки               изменении данных          движок
  Пререквизиты         (BackgroundTasks)
  (source: auto/manual)
       ↑
[FastAPI Backend]
  /admin/*  /recommend/*
       ↑
[React Frontend]
  Треки · Куррикулум · Граф · Дашборд студента
```

---
**[ТЕКСТ]**
> «Вот общая схема. В центре — FastAPI-бэкенд. Слева — PostgreSQL, где хранятся все сырые данные. Справа — Neo4j, графовая база. Связывает их ETL-скрипт: при каждом изменении в PostgreSQL бэкенд запускает фоновую задачу, которая полностью пересобирает граф в Neo4j. Это называется полная ресинхронизация. Мы выбрали этот подход ради простоты: данных у нас академического масштаба, граф умещается в памяти и пересобирается за секунды.»

## СЛАЙД 6 — ETL: PostgreSQL → Neo4j

**Заголовок:** ETL-пайплайн: синхронизация данных  
**Шаги:**
1. `MATCH (n) DETACH DELETE n` — полная очистка графа
2. Создание узлов: `Program`, `Track`, `Module`, `Discipline`, `Student`
3. Связи структуры: `CONTAINS_MODULE`, `PART_OF`, `INCLUDES`
4. Связи студентов: `STUDIES_ON`, `COMPLETED`, `HAS_DEBT`
5. Пререквизиты: `REQUIRES` с атрибутом `source`

**Триггер:** BackgroundTask FastAPI — запускается автоматически после каждого CRUD в admin-роутах

**Тонкость:** `HAS_DEBT` + `COMPLETED` могут сосуществовать на одной паре (Student, Discipline) — долг закрыт пересдачей, Cypher-запрос рекомендаций это учитывает

---
**[ТЕКСТ]**
> «Как данные попадают в Neo4j? У нас есть ETL-скрипт `migrate.py`. При каждом изменении в PostgreSQL — добавлении дисциплины, изменении плана, добавлении пререквизита — FastAPI автоматически запускает этот скрипт как BackgroundTask. Он полностью очищает граф командой `DETACH DELETE` и пересобирает его заново. Почему именно так, а не инкрементальные апдейты? Потому что граф связей очень сильно зависит от структуры, и при изменении одной секции могут поменяться отношения у десятков узлов. Полная ресинхронизация — более предсказуема и проще в поддержке при нашем объёме данных. Интересная тонкость: студент может иметь одновременно связи HAS_DEBT и COMPLETED с одной дисциплиной. Это корректно — значит, он получил долг, а потом успешно пересдал.»

## СЛАЙД 7 — «Умные» пререквизиты: алгоритм

**Заголовок:** Автоматическое построение графа пререквизитов  
**Проблема:** Учебные планы не содержат явных пререквизитов — их нужно вывести

**4 шага алгоритма `build_prerequisites.py`:**

1. **Структурные кандидаты (PostgreSQL)**  
   Пары дисциплин из одного раздела плана, где позиция секции A < позиции B  
   *(SQL: JOIN разделов по позиции)*

2. **Семантическая фильтрация (Jaccard Similarity)**  
   `Jaccard(A, B) = |слова_A ∩ слова_B| / |слова_A ∪ слова_B| > 0.25`  
   Дополнительно: детектирование последовательностей («часть 2», «углублённый»)

3. **Транзитивная редукция**  
   Если A→B и A→C→B, то A→B — избыточна, удаляем  
   *(DFS по построенному графу)*

4. **Запись в PostgreSQL + ресинхронизация Neo4j**  
   `source = 'auto'`, Neo4j получает атрибут `r.source` на ребре `REQUIRES`

---
**[ЭКРАН]** Показать файл `app/management/build_prerequisites.py` в редакторе, либо логи запуска в терминале.

**[ТЕКСТ]**
> «Теперь о самом интересном алгоритмическом решении. В реальных учебных планах явных пререквизитов нет — это просто список дисциплин по семестрам. Мы написали скрипт, который сам выводит логические связи. Шаг первый: берём пары дисциплин из одного раздела, где одна стоит раньше другой по позиции — это структурные кандидаты на связь. Таких пар может быть тысячи. Шаг второй: применяем меру Жаккара — считаем пересечение значимых слов в названиях дисциплин. Если у "Математического анализа 1" и "Математического анализа 2" пересечение больше 0.25 — это явная последовательность. Шаг третий — транзитивная редукция. Если "Матан 1" → "Матан 2" → "Матан 3", то связь "Матан 1" → "Матан 3" избыточна — она выводима транзитивно. Мы её удаляем через обход в глубину. Результат — чистый, минималистичный граф без дублей.»

## СЛАЙД 8 — Neo4j: структура графа

**Заголовок:** Neo4j — граф зависимостей и рекомендаций  
**Узлы и связи:**

```
(:Student)-[:STUDIES_ON]->(:Program)
(:Program)-[:CONTAINS_MODULE]->(:Module)
(:Module)<-[:PART_OF]-(:Discipline)
(:Discipline)-[:REQUIRES {source}]->(:Discipline)
(:Student)-[:COMPLETED]->(:Discipline)
(:Student)-[:HAS_DEBT]->(:Discipline)
(:Track)-[:INCLUDES]->(:Discipline)
```

**Ключевые свойства:**
- `Discipline.semesters: [int]` — список семестров изучения
- `REQUIRES.source: 'manual' | 'auto'` — происхождение связи
- `Program.year: int` — год поступления (для расчёта текущего семестра)

## СЛАЙД 9 — Часть 2: Рекомендационный движок

**Заголовок:** Функциональный блок 2 — Персональные рекомендации  
**Cypher-запрос (упрощённо):**

```cypher
MATCH (s:Student {id: $id})-[:STUDIES_ON]->(p:Program)
MATCH (p)-[:CONTAINS_MODULE]->(m)<-[:PART_OF]-(d:Discipline)
WHERE NOT (s)-[:COMPLETED]->(d)
  AND $next_semester IN d.semesters
OPTIONAL MATCH (s)-[debt:HAS_DEBT]->(d)
OPTIONAL MATCH (d)-[r:REQUIRES]->(req)
OPTIONAL MATCH (s)-[:COMPLETED]->(req)
WHERE debt IS NOT NULL 
   OR all(req IS NULL OR s COMPLETED req)
RETURN d.name, r.source, ...
ORDER BY is_debt DESC, prerequisite_count DESC
```

**Логика:**
- Текущий семестр вычисляется из `Program.year` + текущая дата
- Долги идут первыми (is_debt = true)
- Обязательные → элективы, сгруппированные по блокам

## СЛАЙД 11 — Сравнение СУБД в проекте

**Заголовок:** PostgreSQL vs Neo4j — когда что использовать  

| | PostgreSQL | Neo4j |
|---|---|---|
| **Что хранит** | Структурные данные, история | Граф связей |
| **Что делает лучше** | ACID, FK, JOIN по id | Обход графа, паттерн `(a)-[r]->(b)` |
| **Когда используем** | CRUD, административные формы, граф-редактор | Рекомендации, поиск путей |
| **Язык запросов** | SQL с рекурсивным CTE | Cypher |
| **Роль** | Source of truth | Read-optimised replica |

---
**[ТЕКСТ]**
> «Чтобы подытожить архитектурное решение: PostgreSQL — это источник истины. Все изменения идут в него, там же хранятся сами пререквизиты. Neo4j — это оптимизированная для чтения реплика в виде графа. Запросы на рекомендации было бы очень сложно написать на SQL с рекурсивными CTE — нужно проверять все пути в графе для каждого студента. В Cypher это выглядит натурально и выполняется быстро. Это и есть суть паттерна Polyglot Persistence.»
